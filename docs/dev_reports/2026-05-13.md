## 2. The Google handoff

**File:** `phenodeV3/src/sections/auth/AuthLogin.jsx:53-68`

Replaced the previous `console.info` stub with:

```js
const handleGoogleSignIn = () => {
  const apiBase = import.meta.env.VITE_API_URL || '/api';
  window.location.assign(`${apiBase}/auth/google/login`);
};
```

`window.location.assign` rather than `href = ...` because OAuth requires a real top-level navigation — react-router's `<Navigate>` would do an in-app push that the backend cookie/session machinery doesn't see.

Same handler shipped on `AuthRegister.jsx:35-43` — clicking "Continue with Google" on the register page now also kicks off the OAuth flow. New accounts naturally land at `/approval-pending` because the backend creates the user row with `is_approved=false` (verified at `phenodeX/phenode_backend/api/auth/routes.py:296`), the `/api/auth/token` exchange returns 403 with `detail="pending approval"` (routes.py:307), and `/oauth/callback` detects that and routes accordingly.

## 3. The new `/oauth/callback` page

**File:** `phenodeV3/src/sections/auth/AuthOAuthCallback.jsx` (new, 220 lines)

The end-to-end shape this page closes:

1. User clicks "Continue with Google" on `/login` or `/register`.
2. Browser navigates to `GET ${VITE_API_URL}/auth/google/login`.
3. Backend bounces through Google's consent screen, exchanges the auth code with Google for an ID token, and 302s back to `${FRONTEND_ORIGIN}/oauth/callback?token=<id_token>` (verified `routes.py:118-120`). On Google-side failure it instead sends `${FRONTEND_ORIGIN}/login?error=<reason>` (routes.py:89, 116, 123).
4. **This page** reads the `?token` from the URL, POSTs it to `/api/auth/token`, and dispatches by status.

### Dispatch matrix

Mirrors `AuthLogin.jsx`'s §4 exactly so behavior is identical regardless of how the user signs in:

| Response | Action |
| -------- | ------ |
| `200` | `login(data)` (persists tokens + updates `AuthContext`); preload `useMyDevices` SWR cache; `navigate('/dashboard/fleet-overview', { replace: true })` |
| `403` with `detail` containing `"pending"` | `navigate('/approval-pending', { replace: true })` |
| `403` other | Render themed `Alert` with the backend's `detail`; offer "Back to sign in" link |
| `400` / `401` / other | Render themed `Alert` with the backend's `detail` (or fallback copy) |
| Network failure | Render themed `Alert`: "Network error — please try again." |

### Defensive paths beyond the matrix

- **`?error=<code>` from the backend.** If the backend's OAuth callback already redirected us here with an `error` query (rare but happens when Google denies, the ID token didn't arrive, or the Google token exchange itself fails), skip the `/api/auth/token` call and surface a friendly message via `describeBackendError(code)`. Known codes: `access_denied`, `no_id_token`, `token_exchange_failed`; unfamiliar codes are surfaced verbatim (capped at 80 chars) so we don't swallow useful diagnostics.
- **No `?token` and no `?error`.** Means the user landed on `/oauth/callback` directly (bookmark, refresh after error, etc.). Show "No Google sign-in token was provided. Please start sign-in again."
- **React 18 StrictMode double-invoke.** Guarded with a `useRef` so the `/api/auth/token` exchange fires exactly once per real mount. The endpoint is idempotent on the backend, but double-firing would still produce a confusing UI flicker and an extra audit-log row.

### Visual treatment

- Reuses the same 52×52 logo box, heading typography, and inline `Alert` recipe as `AuthLogin.jsx` so the surface feels continuous when the browser lands here.
- Active state: themed `CircularProgress` (`color: var(--green)`, 32px) under "Signing you in… Finishing the Google handoff. This usually takes a second."
- Error state: themed `Alert` (matches `AuthLogin`'s exact sx — `rgba(247, 72, 122, 0.10)` bg, `1px solid var(--critical)` border, `var(--critical)` text/icon) plus a "← Back to sign in" link that styles like the rest of the auth surface (`var(--blue)` → `var(--green)` on hover).

## 4. Route registration

**File:** `phenodeV3/src/routes/LoginRoutes.jsx:25-30, 65-77`

Two changes:

```jsx
// new import
const AuthOAuthCallback = Loadable(lazy(() => import('sections/auth/AuthOAuthCallback')));

// new child under the AuthWrapper layout route
{
  path: 'oauth/callback',
  element: <AuthOAuthCallback />
}
```

Sits inside the same `AuthWrapper` parent as `/login`, `/register`, and `/approval-pending` so the heavy gradient/`backdrop-filter` chrome stays mounted across the entire auth surface — no re-paint when the browser arrives from Google.

Lazy-loaded like its peers; the callback chunk only loads when the route is hit, keeping it out of the entry bundle (per the Lighthouse baseline `phenodeV3/docs/Lighthouse/baseline.md` §2).

A comment in `LoginRoutes.jsx:69-73` calls out that the path string must stay in sync with `phenodeX/phenode_backend/api/auth/routes.py:119` so any future move of either side is caught.

## 7. What's still out of scope

- **Backend env vars.** This work assumes the local `phenodeX` backend has `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` configured. Without those, Google's consent screen will reject the client. Not a frontend concern; flagged for the backend team.
- **Token refresh on 401.** Still inline in the AuthContext. A unified fetch wrapper that auto-refreshes on `401` is a separate, larger lift documented in the Auth milestone's "out of scope" section.
- **Email/password signup form.** `/register` is still Google-only by design. The backend supports `POST /api/auth/signup` (the `make signup` Makefile target proves it); adding the form is a follow-up.
